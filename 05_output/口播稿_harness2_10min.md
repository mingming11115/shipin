## 开场｜这篇文章是谁做的、有多火（约 300 字 / 75 秒）

[停顿] 先问一个问题：同一个模型，为什么有的 agent 很能干，有的就笨手笨脚？

差别往往不在模型，在 harness——就是包在模型外面的那套提示词、记忆、工具和流程。今天要讲的这篇论文，就是让 agent 自己改这套东西的。论文叫 Harness2：Recursive Agent Harnessing for an Open World，10 月 12 号挂在 arXiv 上。

先说这篇文章是谁提出的。[重点强调] 一作是西北大学的 Ruiyao Xu，其余八位作者全部来自 Google Cloud AI Research——就是 Google 云的 AI 研究团队，做 agent 基础设施的那拨人。也就是说，这是大厂研究团队拿自家 agent 产品线的问题，做的一次相当认真的方法学尝试。

再说热度。代码开源在 Google Research 的 GitHub 上，仓库 10 月 6 号创建，到今天一个多月，[重点强调] 已经涨到两万四千六百多个 star，两千四百多个 fork，一百八十多个 issue 在讨论。什么概念：平均每天三四百个 star，而且社区里已经冒出好几个第三方移植——有人把它接进别的 agent 框架，有人拿它做红队实验。一个多月就有这个生态速度，在研究型仓库里算非常罕见的。

[停顿] 为什么这么火？因为它戳中了所有做 agent 的人共同的痛。下面进入正题。

## 第 1 段｜两个拦路的问题（约 200 字 / 50 秒）

让 agent 自我改进，也就是所谓的 RSI，想法不新，但落到开放世界有两个坎。

第一，真实任务在设计阶段没见过，也没有标准答案。没有对错，你怎么判断这次改动是变好了还是变坏了？这是所有自我改进方法绕不开的判据问题。

第二，以前的改进方法太针对单个任务，换个任务就失效，不会举一反三。经验沉淀不下来，每次都从零开始。

[重点强调] Harness2 的回答是两级递归：改做事的方式，也改改进的方式。这两个"改"缺一不可，后面我会展开讲它们怎么咬合。

多说一句"harness"具体指什么。你们每天在用的 agent 产品里，那些系统提示词、长期记忆文件、工具使用规范、技能库、子代理配置——全是 harness 的组成部分。论文里它被拆成八类可编辑的组件，每一类就是一个文件。这也埋下伏笔：既然 harness 全是文件，那"改 harness"就可以变成一个可验证的编辑过程。

## 第 2 段｜看图：蓝色区，任务级递归（约 260 字 / 65 秒）

[看图表] 看这张总览图。上面蓝色区是第一级：任务级递归，针对当前任务改 harness。

流程是编号的一到四。一，executor 先用现有 harness 跑一遍任务，留下执行轨迹，这是参照。二，Harness Editor 提出两个候选 harness：一个只动通用维度——规划方式、工具组织、上下文管理——叫 invariant；另一个动领域知识、业务流程，叫 domain-specific。

三，把两个候选都放到同一个任务上重跑一遍，拿到各自的执行证据。四，Composer 把两个候选里真正起作用的部分，合成一个最终 harness。

[重点强调] 注意整个过程，模型一个字都没动——参数冻结，改的全是外面这套流程文件。这也是它即插即用的根源：任何模型、任何框架，只要 harness 是文件形式的，就能套这套方法。

## 第 3 段｜关键设计：比行为，不比对错（约 240 字 / 60 秒）

[翻页] 这里有个关键设计，也是我觉得全文最聪明的一步。[重点强调] 判断候选好坏，靠的是行为对比，不是标准答案。

原理是这样的：因为候选里有那条 invariant——它刻意不碰领域逻辑——所以它天然是个参照物。同样的任务，invariant 轨迹和 domain 轨迹摆在一起，行为差异就说明了领域改动的实际效果。也就是说，不知道正确答案，也能判断这次改动值不值得采纳。

打个比方：你想知道新调料有没有用，就做两锅只差这一味料的菜，尝差别就行——不用知道"标准味道"是什么。

而且不是每个候选都会被采纳，Composer 会把没用的候选直接扔掉，宁可不改也不乱改。[停顿]

那能不能再多改几轮？这就引出预算 k。

## 第 4 段｜budget k：递归可以加码（约 220 字 / 55 秒）

这一步可以重复，叫 budget k。论文试了两种加法：并行递归，k 个候选一起改，最后合并；串行递归，改完一轮，带着全部证据改下一轮，像滚雪球。

两种加法各有脾气。并行适合改动互不干扰的场景，k 个方向一起探，最后 Composer 挑好的拼起来；串行适合"后一步要建立在前一步结论上"的场景，每一轮都站在上一轮的肩膀上，但坏处是一轮跑歪、后面全歪，所以它对行为对比判据的要求更高。

实测数字很清楚：并行递归在编程域从 76.5 涨到 80.8，办公域从 79.5 涨到 83.4。[重点强调] k 从 1 加到 5，分数一路往上走——说明性能提升不是靠一次好运，是探索越多、收获越稳定。

论文还算了一笔成本账：统计的是每个任务的总 token 开销，不是只算最终那次调用。所以"多花算力换分数"这笔交易是明码标价的，不是白烧。

## 第 5 段｜紫色区：框架级递归（约 260 字 / 65 秒）

[看图表] [翻页] 但任务级递归只解决了一个任务。真正让方法立住的，是下面紫色区：框架级递归。

每个任务结束，Reflector 来复盘：这次哪些 harness 被采纳了、为什么起作用、有哪些教训，写成改进记录，更新到 Improvement Library。注意图上的雪花标记，[放慢] 它的含义是：任务进行中，这套改进机制是冻结的；任务结束后才更新。这就避免了边干活边改规矩——干活的人不能自己给自己发奖金。

图上那两条虚线，一条把改进记录存进库，一条把经验带回给下一次任务。[重点强调] 这就是两级之间的耦合：任务级递归负责把当前任务做好，框架级递归负责越做越顺手。

消融实验证明这不是摆设：去掉经验库，三个域的分数全都往下掉；而在小预算下积累的库，换到新任务上还能继续贡献——经验是真的迁移过去了。

## 第 6 段｜实验：三个基准、四种配置（约 240 字 / 60 秒）

[重点强调] 效果怎么样？论文在三个专业基准上验证：WorkBuddy-Bench，覆盖编程、网页、办公三个域的八十个真实任务；JobBench，六十五个职业任务；还有 Harvey 的法律智能体基准 LAB，一千二百五十一个法律任务、覆盖二十四个执业领域。

四种"模型加 harness"的配置都测了：两套开源底座，配 GLM-5 和 Gemini 3.5 Flash。结论一致：一步改进，全面超过基线。

具体数字：WorkBuddy-Bench 涨了最多 11.5 分，JobBench 涨 4.5 分，LAB 的部分通过率涨 11.8 个百分点。对比的对手里有 Meta-Harness 这种需要离线训练数据的强基线——Harness2 用在线的方式超过了它。

代价也说一句：多轮递归会多花 token，论文专门画了成本曲线，这笔账算得很诚实。

## 第 7 段｜边界与局限（约 160 字 / 40 秒）

[翻页] 讲完优点讲边界。论文自己列了局限：第一，行为对比的判据在噪声特别大的任务上还没系统验证——如果任务本身方差就大，两条轨迹的差异可能只是运气；第二，改进库目前是领域内的，跨大领域的迁移只做了初步实验，从法律任务搬到编程任务会怎样，还是未知数；第三，编辑器本身也是模型，harness 改坏了怎么办，靠的是守门规则和 fail-safe 机制兜底——校验不过关的提议会被整包丢弃。

[停顿] 这些都不致命，但如果你想落地，得先想清楚自己的任务噪声有多大。

## 收尾与行动号召（约 200 字 / 50 秒）

[停顿] 回到开头。Harness2 的答案一句话就能说完：[重点强调] 改进 agent 的"做事方式"，同时改进"改进方式"本身——前者是任务级递归，后者是框架级递归，两条环咬在一起转。

为什么它一个多月能拿两万四千个 star？因为模型能力已经卷得差不多了，下一步的增量在 harness 上，而它给出了第一个在开放世界里可验证的、自动改 harness 的完整方案。模型不动，改的全是外挂文件，即插即用——对每一个正在被"同一个模型为什么时好时坏"困扰的团队，这都是一条立刻能试的路。

代码已经开源，github 上搜 google-research slash harness2 就有。

我讲完了。接下来想听听大家的看法——尤其是这个行为对比的思路，搬到我们自己的场景里能不能用。

## 一页纸摘要（备用）

【一句话结论】Harness2 用两级递归让 agent 在没有标准答案的任务流上自我改进 harness：改"做事方式"也改"改进方式"。

【来头与热度】西北大学 Ruiyao Xu + Google Cloud AI Research 八人团队，arXiv 2026-10-12；GitHub 仓库 10 月 6 日创建，约 6 周 24.6k star / 2.4k fork，社区已有多个第三方移植。

【三个支撑】
1. 任务级递归：Propose–Probe–Compose，用行为对比代替正确性判据，一步最高 +11.5 分（WorkBuddy-Bench）
2. 框架级递归：Reflector 更新改进库（❄ 任务中冻结、任务后更新），经验跨任务复用，+11.8pp（LAB）
3. 即插即用：模型不动、只改外挂 harness；预算 k 加大持续涨（76.5→80.8 / 79.5→83.4）；代码开源

【我要什么】组会后定一件事：挑一个我们自己的任务类型，跑一轮行为对比做可行性验证。

【风险与兜底】行为对比在强噪声任务上未系统验证；兜底是先用 invariant 锚点人工复核一轮。

【时间线】读案例附录（Appendix E.7）→ 下周出验证方案。
